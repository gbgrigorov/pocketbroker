1 Request path & cache tiers

There is no Redis and no external cache server. Caching happens at three independent layers, each with a different lifetime and a different reason to exist. A request only reaches Postgres if all three miss.

Tier 1 · browser

Vue 3 SPA

sessionStorage

  • pb:graph:v1 — ~1 MB ownership graph 30 min TTL
  • pb:graphpos:v1 — settled node coordinates, so the constellation redraws instantly
  • sessionStorage, not localStorage: survives refresh, dies with the tab, never writes the people graph to disk
  • Quota errors are swallowed — caching is skipped, behaviour is unchanged
Edge

nginx

:443 → TLS (certbot)

  • / → /var/www/pocketbroker static SPA bundle
  • try_files $uri $uri/ /index.html — real files win; unknown paths fall back to the SPA router
  • /api/ → reverse proxy to 127.0.0.1:8000
  • Serves sitemap.xml / robots.txt straight off disk
Tier 2 · process

FastAPI

uvicorn · systemd pocketbroker-api · bound 127.0.0.1 only

  • _cities_cache — single list ∞
  • _map_cache{city} — per city slug ∞
  • _entities_cache — pre-sorted browse rows, so type-ahead never hits the DB
  • _entity_signal_counts_cache — id → tier counts, bulk-computed in 2 queries
  • _graph_cache{limit} — ~250 ms of DB work each; bounded at 4, evicts oldest-first
ORM

SQLAlchemy 2

Mapped[] / declarative · Alembic migrations

  • Session per request via Depends(get_session)
  • Auth gate sits outside the cache — anonymous callers get 401, never a cached body
  • Depth-bounded traversal computes indirect ownership paths at query time
Tier 3 · store

PostgreSQL

bg_realestate · 24 tables

  • Only reached on a full three-tier miss
  • Written exclusively by the ETL — never by a crawler
  • Postgres runs its own buffer cache underneath all of this

1b How each tier is invalidated

Browser

Expires on its own after 30 min. Also dropped immediately by authStore.setToken() on any token change — login, logout, or a token the server rejected — because the graph is login-gated people data that must not outlive its session. Bump :v1 when the payload shape changes.

Process

POST /api/admin/refresh-cache calls clear_caches() and drops all five at once. Guarded by the ADMIN_TOKEN env var and fails closed when it is unset, so it can never be hit on a misconfigured deploy. This is the no-redeploy path after an ETL run.

Restart

The caches are plain module-level dicts, so systemctl restart pocketbroker-api clears everything by definition — and the deploy already restarts. That makes the correctness floor "a deploy fixes it", with the admin endpoint as the fast path.

The trade-off worth naming

A single uvicorn process means a single shared cache — no cross-worker coherency problem, and no Redis to operate. The cost is that the cache is per process: scaling to multiple workers would need the cache moved out, or each worker warms its own copy. That is an acceptable trade at this traffic level, and it is deliberate rather than accidental — the data is refreshed monthly by ETL, not continuously by users, so an unbounded TTL with explicit invalidation is the right shape. The one cache keyed by caller-supplied input (_graph_cache, keyed by limit ∈ 1..2000, ~1 MB per entry) is explicitly bounded at 4 entries, because otherwise walking the limit range would pin gigabytes.

2 The schema — 24 tables, 6 clusters

Crawlers never touch Postgres. They append dated JSONL into data/raw/; the ETL in backend/etl/ normalises and upserts from there. That keeps every scrape replayable — the whole database can be rebuilt without re-crawling.

Developer graphthe centrepiece — a self-referential ownership network
entityid, kind ('company' | 'person'), eik (unique), name, name_normalized, slug, person_key, is_builder, legal_form, status, address, capital_bgn, founded_year, has_seizure  — 25 cols
entity_edgeid, src_entity_id → entity, dst_entity_id → entity, relation ('ownership' | 'management'), share_pct, role, valid_from, valid_to, is_current, source  — unique(src, dst, relation, valid_from)
entity_signalid, entity_id, subject_kind, matched_name, matched_eik, matched_person_key, source_type, tier, match_confidence, title, snippet, url, source_site, observed_date  — unique(url, matched_name)
builderid, entity_id → entity (1:1), eik (unique), name, hq_city_id, capital_bgn, financials, ksb_category, ksb_active, insolvency_flag, tax_debt_bgn, last_checked_at

One table holds both companies and people. Companies key on eik (the Bulgarian company number); people have no national id, so they key on a derived, deterministic person_key. That single choice is what makes the graph work: entity_edge is a self-referential edge table, so "person owns company owns company" is the same query shape at every hop. Only direct edges are stored — indirect links are graph paths computed by a depth-bounded traversal, so no denormalised closure table can drift.

entity_signal is evidence attached to a node — a court act, a registry flag, a forum post — carrying a tier and a match_confidence, because a name match is not proof of identity. The unique constraint on (url, matched_name) is what stops one court act, which may name many companies, from being written once per entity and double-counted.

builder is an extension row, not a duplicate: a builder is an entity of kind company with is_builder set, joined 1:1 through builder.entity_id. It carries only the rich profile fields — КСБ licence, insolvency flag, tax debt, financials — that would otherwise sit null on every person row in entity.

Projectsnew buildings
new_buildingid, city_id, neighbourhood_id, canonical_key, name, developer_id → builder, developer_name, akt_stage, completion_year, floors, materials, price_eur_sqm, area_min/max_sqm
new_building_sourceid, new_building_id, site, source_name, url, price_eur_sqm, scraped_at

The same development is listed on several portals under slightly different names, so canonical_key deduplicates it into one new_building row and each portal's listing is kept as a new_building_source child — preserving per-site prices and the evidence trail. developer_id is the join into the ownership graph: from a building you reach the developer, its owners, and their court signals.

crawl_run is observability, not data — every scrape logs pages, bytes, parse/emit counts and errors, so a silently-failing crawler shows up as a run that emitted zero.

court_check records that a check ran and what it found — including zero results. Without it, "no court acts" and "never looked" are indistinguishable. sync_log audits the local→prod research push, and its dry_run flag reflects that the push tool defaults to dry-run.

Reading the whole thing in one sentence

Public sources → crawlers → append-only JSONL → ETL → 24-table Postgres, where a self-referential entity graph links people to companies to buildings to court records; served by FastAPI behind nginx, with an in-process cache that turns the two expensive endpoints (/map, /graph) into dictionary lookups and is invalidated explicitly after each ETL run.
